## 文件抽象
操作系统设计者意识到绝不能让用户直接面对物理存储的复杂性，于是设计了一个抽象层，即文件系统。几个重要的抽象概念：文件、目录、链接。

对于操作系统来说，最重要的抽象概念就是文件。用户直接操作文件，操作系统负责将文件映射到物理的磁盘存储之上。这种抽象带来了几个好处
* 方便记忆：不再需要记住物理位置，只需要记住 xxx.docx 等有意义的名字
* 简化编程：open/read/write/close 简单几个系统调用，就能操作所有存储设备
* 强一致性：程序可以在硬盘上开发，然后不经修改就运行在U盘、光盘、或网络存储上

Unix/Linux系统将文件这个抽象发挥到了极致，在Unix/Linux系统中，“一切皆文件”，任何可以通过 read()、write() 操作的对象，都可以被抽象为文件。
- 设备文件：/dev/sda 代表整个硬盘，/dev/tty 代表终端。读写这些“文件”就是在操作硬件
- 命名管道：/tmp/myfifo 进程间通信的通道，外观和操作方式都跟文件很像
- proc文件：/proc/cpuinfo 看起来是个文件，读它得到的是CPU信息；/proc/meminfo 得到内存信息。实际上它们是内核数据的动态视图

当进程通过 open() 系统调用打开一个文件时，操作系统会返回一个文件描述符（File Descriptor），这是一个非负整数（通常是0、1、2、3...）。文件描述符是进程级别的，每个进程都有自己的文件描述符表，保存已经打开的文件描述符。
想象一下，如果没有文件描述符，每次读写文件时，你都需要：
- 重新解析文件路径（逐级查找目录）
- 重新检查访问权限
- 重新查找文件在磁盘上的位置

这个过程的性能开销是巨大的！文件描述符的巧妙之处在于，它将所有“昂贵”的操作集中到 open() 系统调用中完成，后续的读写操作只需使用这个简单的整数句柄。除此之外，文件描述符的优点包括提供一种统一的方式，来访问各种类型的“文件”（包括设备、管道、套接字等）。

当进程启动时，默认打开三个文件描述符：
- 0 - 标准输入（stdin）：默认从键盘读取
- 1 - 标准输出（stdout）：默认输出到屏幕
- 2 - 标准错误（stderr）：默认输出错误信息到屏幕

在文件系统中，目录被当做一种特殊类型的文件。这种统一性带来了巨大好处：
* 代码复用：操作系统可以用几乎相同的代码处理目录和普通文件
* 权限统一：目录和文件使用相同的权限模型（rxw读写执行、用户组等）
* 实现统一：存储方式都一样

只不过目录中存储的内容不是普通的数据，而是一系列目录项，每个目录项包含一个文件名和对应的inode编号，inode编号是一个文件的唯一标识，通过它可以找到inode，里面保存了文件的详细信息，通过inode又可以找到数据块，数据块中存储着数据。

在文件系统中，链接（Link）是一种让多个文件名指向同一个文件内容的方法。链接分为两种：硬链接（Hard Link）和符号链接（Symbolic Link，也称软链接）。

硬链接是多个目录项指向同一个inode。由于inode是文件的唯一标识，所以硬链接实际上是给同一个文件起多个名字。

硬链接的实现很简单：在目录中创建新的目录项，指向同一个inode，并将inode的链接计数加1。

硬链接的特点
* 共享 inode
* 无法区分原件：所有链接地位平等
* 链接计数：inode中记录有多少个硬链接指向它
* 删除规则：只有当所有的硬链接都被删除，文件才真正被删除
* 限制：不能链接目录（避免循环）

软链接的实现也不难：需要创建一个新的inode（跟硬链接最大的不同），类型为符号链接，inode对应的数据块中存储的是一个路径字符串，指向另一个文件或目录。

软链接的特点
* 有自己的inode，是一个独立的文件，只是内容存储的是目标路径
* 删除原始文件，软链接就会变成悬空链接（dangling link），指向不存在的文件
* 软链接可以链接到目录

## 存储结构
数据块这一层的主要是隔离物理磁盘的差异性。因为不同的磁盘上，扇区的大小不一定是相同的，有的是512字节，有的是4096字节。数据块的大小通常是固定的，以常见的4KB数据块为例，如果磁盘的扇区大小为512字节，那么一个数据块对应8个扇区，如果扇区大小为4096字节，那么一个数据块就对应一个扇区。当然不同的文件系统其数据块大小也可能不同（如1KB,2KB,4KB等）

数据块是文件系统存储的基本单元。也就是说，如果一个文件的数据大小不足4KB，它也会独占一个4KB的数据块。

当一个文件需要保存时，怎么分配数据块给这个文件呢？

顺序分配：每个文件占用连续的几个数据块，实现简单，而且是连续存储，顺序访问时，效率非常高，但问题是
* 存储碎片：删除文件会产生空洞
* 扩容困难：文件数据可能会增长，当文件变大时，只能帮文件重新找更大的连续空间，并复制数据
* 预分配难：避免耗时的扩容，预先分配足够的空间，那么预分配空间小了不够用，大了浪费空间

链式分配：给每个文件分配多个分散的不连续的数据块来存储数据，每个块包含数据和指向下一个块的指针。但它的问题是
* 随机访问灾难：要读第1000个块，得从头遍历999个数据块
* 可靠性问题：一个数据库损坏，后面的数据都丢失
* 空间开销：每个数据块都要存储指针，通常占4字节

既然数组不行（顺序分配）、链表不行（链式分配），于是就有了索引分配这种方案，这个方案里最重要的一个概念就是inode（索引块）。

每个文件对应一个inode，inode里存储了分配个这个文件的所有数据块指针（数据块号）。这里需要注意的是inode的大小是固定的，一般是256字节。我们可以通过目录树，可以找到一个文件对应的inode编号，通过inode编号可以找到inode，那么现在的问题是，怎么通过inode编号找到inode呢？

其实一个系统中所有的inode是并排连续存储，可以想象成一个inode数组，inode编号就是inode数组的下标。通过下标可以快速找到对应inode，这也是为什么inode大小要固定的原因。

那么关键问题来了，inode只有256字节，一个数据块号占4字节，顶多也就只能存储256/4=64个数据块号，一个数据块大小4KB，也就是说文件最大支持64*4KB=256KB，超过这个大小，inode中就没有空间存储对应的数据块号了。

于是操作系统设计师，在inode中通过多级指针实现了多层索引。inode中存储的信息是非常多的，主要是文件的一些元数据信息。其中，存储数据块信息的是一个60字节的i_block[15]，这就是刚提到的多级指针。它存储了指向文件数据块的15个指针（12直接、1个一级间接、1个二级间接、1个三级间接）
* 直接指针（前12个）：每个指向一个数据块（通常4KB）。因此可存储：12 × 4KB = 48KB 文件数据。
* 一级间接指针（第13个）：指向一个特殊的数据块，即指针块，该块包含1024个（指针4字节，块4KB）数据块指针，这1024个指针指向1024个用来存储文件数据的数据块。因此一级间接指针可以存储：1024 × 4KB = 4MB 文件数据
* 二级间接指针（第14个）：它指向一个指针块，该块的每个指针又指向一个指针块。因此，二级间接指针可以存储：1024 × 1024 × 4KB = 4GB 文件数据。
* 三级间接指针（第15个）：这个大家自行脑补或者看图吧，不好描述了，三级间接指针可以存储 1024 × 1024 × 1024 × 4KB = 4T 文件数据。

也就是说，通过这15个指针，总共可以存储大小为 48KB + 4MB + 4GB + 4T 的文件数据，也就是说，最大支持的文件大小约为4TB。除此之外，我们还发现一个规律，指针级数越高，对应需要访问的指针块越多，效率越低。因此，在存储文件的时候，前48KB会存储在直接指针指向的数据块、接下来的4MB会存储在一级间接指针指向的数据块，以此类推。这种层次化设计，既照顾了常见的小文件，又支持了极端的大文件，体现了优秀的工程权衡。

文件系统把整个数据块数组划分成了好几个功能不同的区
- 引导块：存储启动代码。计算机启动时，BIOS先读这里。
- 超级块：存储了一些全局信息，比如总块数、空闲块数、inode位图所在的起始数据块号和长度、块位图所在的起始块号和长度、inode表起始数据块号和长度、数据区的起始数据块号等等。
- 块位图：是一个位图，一个位对应一个数据区的一个数据块，如果这个块没使用，这一位对应值为0，相反，则为1。通过块位图，可以快速的找到空闲的数据块，分配给文件使用。
- inode位图：也是一个位图，作用跟块位图类似。当我们创建一个文件的时候，要从inode表中找到一个空闲的inode，分配给这个文件使用。inode位图就是为了快速找到空闲的inode。
- inode表：这个是一个预先分配好的长度固定的inode数组。这个inode表具体有多少个inode，这个是有一定算法计算出来的，待会再讲。
- 数据区：这个就是真正存储文件数据的地方了，不过有个例外，inode的指针块也放到这里。

我们再来看下inode表。假设一个1TB的ext4硬盘，采用默认设置（大约每16KB数据分配一个inode），那么：
- 总 inode 数 ≈ 1TB / 16KB ≈ 6千5百万个
- inode 表总大小 = 65,000,000 × 256 字节 ≈ 15.5 GB

注意：这15.5 GB是元数据开销，它占据了磁盘空间，但不存储任何用户文件的实际内容。这就是为什么有时会出现“磁盘还有空间，但inode已用尽”的情况。即数据块有空闲，但inode表被无数个小文件耗尽了。

## Page Cache
磁盘访问速度是毫秒级别，相比CPU周期的纳米级是相当慢速的。于是想出了很多优化文件读写的方法，其中一个就是利用内存作为缓存，即Page Cache。

缓存之所以起作用，主要是基于两个局部性原理
* 时间局部性：刚访问的数据很可能再次被方案
* 空间局部性：访问某个位置后，很可能访问附近位置

Page Cache直接构建在物理内存这个层面上，它有操作系统内核来管理，用于缓存磁盘上的文件数据，它是以物理内存页（通常为4KB）为单位缓存数据，这些页对应着文件中的数据块。Page Cache以文件为单位组织这些内存页和数据块之间的关系。每一个文件对应一个页缓存树（Radix Tree基数树，也叫压缩前缀树，比较高级的数据结构，感兴趣的话自己去查吧）。在这个树中的节点的Key是页索引，Value是内存页。

这里解释一下什么是页索引。因为文件系统是按照数据块（4KB）来读取数据的，也就是说，即使你访问很少的数据，它也是读取一个数据块，也就是4KB的数据。我们在缓存的时候，也就按照这个数据块作为单位来去缓存。逻辑上，我们把文件分割成一个一个连续的4KB的数据块，从0开始，给每个数据块编号（0、1、2、3...），因为一内存页就等于一数据块，因此，数据块的编号0、1、2、3...也叫做页索引。

当我们想要从文件中读取数据时，文件系统会尝试从Page Cache中查找对应的页。查找过程如下：
1. 根据文件偏移量计算页索引。页索引 = 偏移量 / 4096。
2. 在页缓存树中查找该页索引对应的页。
3. 如果找到，返回该页。
4. 如果没有找到，则需要从磁盘读取数据，并分配一个新页，将其插入到页缓存树中。

除了使用Page Cache缓存文件数据，多次访问相同文件数据时，避免重复访问磁盘，Page Cache加速读取速度的方法还有数据预读。当你顺序读取文件时（比如播放视频），文件系统会进行预读：提前读取你接下来可能需要的块。这个简单的策略效果惊人。我们做个对比。

没有预读的情况：
1. 应用程序请求数据块1
2. 系统读取数据块1（可能需寻道+旋转）
3. 应用程序处理数据块1，然后请求数据块2
4. 系统读取数据块2（再次寻道+旋转）

有预读的情况：
1. 应用程序请求数据块1
2. 系统读取数据块1，同时预读数据块2、3、4...
3. 应用程序处理数据块1，然后请求数据块2
4. 数据块2已在缓存，立即返回
5. 后台继续预读数据块5、6、7...

对比两种情况，有预读的情况，访问磁盘的次数明显减少。我们知道，相对于内存，磁盘是非常慢速的设备，减少磁盘的访问次数，读文件的性能随之提高。实际上，现代文件系统不仅预读，还根据访问模式（通过分析应用程序历史访问此文件的规律来推测访问模式）动态调整预读大小。顺序访问时，增加预读窗口。随机访问时，减小预读窗口，避免浪费。

以上讲的都是Page Cache加速「文件读」的方法，接下来，我们再来看，Page Cache如何加速「文件写」。

程序写入数据时，先写入Page Cache，写入成功后就立即返回。被修改过的页被标记为脏页，脏页会串联在一个脏页链表中，操作系统会定期（Linux下默认为5秒）扫描脏页并写入磁盘。当然，当内存压力比较大的时候，操作系统也会提前强制刷新脏页并释放内存。除此之外，操作系统也提供了系统调用（fsync()）给应用开发程序员，在写入缓存之后强制立即落盘（写入磁盘）。

如果写入Page Cache的数据，在没有落盘之前，操作系统发生崩溃（包括计算机宕机、断电等等），这部分数据就会丢失。

这里我们再回忆一下，其实，在《计算机组成原理》课程中，我们还讲到，磁盘内部也有缓存（专门的SRAM硬件），缓存写入的数据。不过，磁盘缓存跟Page Cache有所不同。数据写入磁盘缓存之后，即便计算机宕机、断电等等，数据仍然不会丢失，并会安全的写入磁盘。这是怎么做到的呢？

## 内存映射文件
内存映射文件是需要程序员主动编程使用的（通过mmap()系统调用），并非Page Cache那样是一个底层的默认实现，它不仅仅是一种性能优化，更是一种新的文件读写编程模型。

当调用read()的时候，文件先从磁盘中读取，然后放置到Page Cache中，注意，Page Cache是操作系统内核管理的，因此，为了内核安全，用户程序是无法访问的。操作系统内核会将Page Cache中的数据，再拷贝到用户空间（也就是代码中的buffer），才能被用户程序访问。

同理，当调用write()的时候，数据先从用户空间（也就是代码中的data），拷贝到Page Cache，对应的物理页标记为脏页，操作系统内核会异步将Page Cache中的脏页写入磁盘。

你看，在以上流程中，read、write系统调用会包含数据在用户空间和Page Cache之间来回拷贝，如果要读取1GB大小的文件，那么就要拷贝1GB的数据，这个拷贝的工作显然是比较耗时的。于是，操作系统设计者们就开始考虑：如果不进行拷贝，直接让用户程序操作（写入和读取）Page Cache，是不是就更高效了呢？

想法很好，但是用户程序是无法直接访问物理页面的？为什么？因为中间还隔了一层抽象层：虚拟内存，虚拟内存再通过页表转换成物理页，从而实现对物理页的间接访问。这也难不倒操作系统设计者，他们将虚拟内存中的用户空间部分，划定出一片地址空间（大小跟文件一样大），让它直接映射到Page Cache中的物理页（之前是不可能映射到Page Cache的，而是其他物理页），这样，用户程序访问这块虚拟地址空间，就相当于访问了Page Cache。

内核会在调用进程的虚拟地址空间的用户空间部分，找一段空闲的虚拟地址区域，并将其对应的所有页表项标记为invalid。内核会在VMA中记录这个映射关系，即这段虚拟地址区域与哪个文件的哪个部分（偏移量）相关联。VMA（Virtual Memory Area，虚拟内存区域）是内核用于描述进程虚拟地址空间中一段连续区域的数据结构。

当进程第一次访问映射区域的某个页面时，会发生缺页异常。内核处理缺页异常时，通过VMA，发现此缺页属于一个内存文件映射。于是，便去Page Cache中查找。
- 如果在Page Cache中找到对应的物理页面（假设物理页号为A），说明文件的对应数据块已经加载到Page Cache，然后，将虚拟页对应的页表项的物理页号设置为A，也就实现了：这个虚拟页指向了Page Cache中的物理页。
- 如果在Page Cache中没有找到对应的物理页面，就会先从磁盘中加载数据块到Page Cache（分配一个物理页面，假设页号为B，然后从磁盘读取数据到该页面，然后将该页面加入Page Cache），最后，再将虚拟页对应的页表项的物理页号设置为B。

大多数情况下，使用write/read就够了，只有在一些极端情况下，比如处理一个大文件，并且频繁随机读写数据片段来进行一些操作时，就比较推荐使用mmap，原因如下

## 虚拟内存
如何在有限的物理内存中，为多个进程提供安全、高效、看似无限的内存服务？虚拟内存就是操作系统给出的完美解决方案。

如果没有虚拟内存，多个程序要共享一块物理内存，最直接的方案是什么呢？
* 排队使用：微信运行时，Word就必须完全退出，数据存到磁盘。但这显然无法接受
* 平均分配：把物理内存切分成固定区域，每个程序分一块，但问题来了，程序大小各异，给小程序分配大块内存空间造成浪费，给大程序预留的空间可能不够
* 动态分配：按需分配大小可变的内存块。这解决了固定大小的浪费和不足的问题，但又催生了新的问题：内存碎片。

在虚拟内存出现之前，操作系统尝试过直接管理物理内存的各种方法，但都面临几个严峻挑战：
* 内存碎片
* 地址冲突
* 内存不足
* 安全漏洞

于是，操作系统设计者们便发明了“虚拟内存”这一中间层。虚拟内存的核心思想如下：

操作系统给每个进程分配一个完全独立的、私有的、完整的、连续的虚拟内存地址空间，比如32位操作系统上虚拟内存地址空间为0~4GB。进程可以随意使用，从地址0开始加载代码，在地址X处存放数据，进程之间互不干扰。

不同进程的虚拟内存地址映射到不同的物理内存地址，这样任一进程都无法有意或者无意访问另一个进程的内存空间。一个进程的任何操作，都无法直接触及到其他进程的数据。一个程序的崩溃，被严格限制在自己的“平行宇宙”里，不会波及系统和其他程序，保证了进程之间的安全和隔离。

程序员从此可以摆脱物理内存具体布局的困扰。无论实际物理内存是8G还是64G，无论是哪家品牌的内存条，程序员看到的都是一个统一的、从0开始的线性地址空间。编译器、链接器可以假设程序从地址0开始装载。它们不再需要关心“这段代码最终会被加载到物理内存的哪个角落”。这统一了开发环境，降低了软件复杂性。

除此之外，**虚拟地址空间可以做得比物理内存大得多，比如在32位系统上，每个进程有4GB虚拟空间，而物理内存可能只有1GB**。你可能会好奇，这是怎么做到的？这其实就是我们后面要讲到的页面置换技术。

MMU（内存管理单元），是CPU中一个专用硬件，它的核心职责就是实时、高速的进行虚拟内存到物理内存地址的翻译。
* 当你的程序执行一条执行，比如 mov [0x1234], eax（将 eax 寄存器的值存入地址 0x1234），这个 0x1234 是虚拟地址
* CPU把这个虚拟地址交给 MMU
* MMU根据一套操作系统内核制定的映射规则，瞬间将这个虚拟地址翻译成物理地址，比如0x87546545
* 最终数据被写入物理地址 0x87546545 所对应的真实内存地址

这个映射规则需要解决原始直接管理物理内存所无法解决的所有问题（安全、隔离、内存碎片、内存不足等），这套规则就是：分段机制、分页机制、以及页面置换。

## 分段机制
操作系统通过虚拟内存为每个进程创造了安全、独立的平行宇宙。关键问题是：MMU做地址转换时，需要参照映射规则，这套规则是如何设计的？最早的映射规则采取分段机制，不过现如今已经部分退出历史舞台，被更加优秀的分页机制所替代，但它仍然有很好的学习价值。

为什么需要分段？每个进程独占一个很大的虚拟内存空间，比如32位操作系统上，虚拟内存空间的大小是4GB，我们需要将每个进程的整个虚拟内存空间都映射到物理内存吗？答案是不行也不需要，毕竟物理内存空间有限，而且一个进程对应的程序在运行过程中所需要的内存（代码段、数据段、堆栈）也是有限的，比如只需要100mb，并不会用完所有的虚拟内存空间，我们只需要对程序所使用的内存进行映射就可以，

比如一个简单的C程序
```c
#include <stdio.h>
int global_data = 42; // 将进入数据段
int uninit_data; // 将进入 bss 段

int main() {
    int local_var = 10; // 在栈上分配
    int *heap_ptr = malloc(100); // 在堆上分配
    return 0;
}
```

编译后，这个程序在虚拟内存中会被组织成多个段：
- 代码段（.text）：存放代码，是只读的。
- 数据段（.data）：存放初始化了的全局变量。
- BSS段（.bss）：存放未初始化的全局变量。
- 堆（heap）：用于程序运行时动态申请内存（如malloc），向高地址增长。
- 栈（stack）：用于函数调用、局部变量，向低地址增长。

现在，我们有两个内存地址映射方法。
- 第一种方法是：我们将整个程序需要的内存空间直接映射到一块连续的大的物理内存。
- 第二种方法是：我们将程序中的每个段（代码段、数据段、BSS段、堆、栈）各自分别映射到一块连续的小的物理内存。

答案是，计算机科学家选择了后者。这就是分段机制的由来。为什么要按照“段”来映射，而不是直接映射整个程序？是因为每个段的访问模式不同，保护需求也不同。代码段应该只能执行和读取、不能写入（防止意外修改指令）。数据段需要读写，但不能执行（防止数据被当成代码执行）。如果我们把整个程序映射为一个连续块，就很难为不同部分设置不同的访问权限。分段让我们可以为每个逻辑单元设置独立的保护策略。

一个进程的每个“段”映射到不同的物理内存，那么，如何记录这种映射关系呢？操作系统内核为每个进程维护一张段表（在x86架构中称为段描述符表）。段表中记录了每个段的关键信息（段描述符）。每个段描述符包含如下信息：
- 段基址：这个段从物理内存的哪个地址开始
- 段界限：这个段的大小（边界）
- 访问权限：可读、可写、可执行等标志
- 其他标志：如是否存在于物理内存中、特权级等

在x86架构的分段模型中，BSS段（未初始化的全局变量）通常与已初始化的数据段（.data段）合并在一起，共享同一个段描述符，统称为数据段。

段表是操作系统内核维护的数据结构，你可以把它简单想象成一个数组。在进程的PCB中，通常会有一个字段存储段表的内存地址。当进程切换时，操作系统从PCB中取出这个值，加载到一个寄存器（LDTR，局部描述符寄存器）中。这样，CPU就知道去哪里找当前进程的段表了。有了段表，就可以实现接下来的地址翻译了。

那么，如何借助进程的段表来实现虚拟地址到物理地址的翻译的呢？

在分段系统中，一个虚拟地址（更准确地说是逻辑地址）由两部分组成：
- 段选择符：指定要访问哪个段（是一个索引，借助它从段表中查找段描述符）
- 段内偏移：指定要访问该段内的哪个位置

实际上，段选择符通常并不直接出现在指令的地址中！在x86架构中，段选择符存储在段寄存器中，而指令中只给出段内偏移。x86架构中有6个段寄存器：
- CS（代码段寄存器）：指向当前正在执行的代码段
- DS（数据段寄存器）：指向默认的数据段
- SS（栈段寄存器）：指向栈段
- ES、FS、GS：额外的数据段寄存器

当CPU执行指令时，它会根据指令的上下文自动选择段寄存器：
- 取指令时，使用CS:IP（CS提供段选择符，IP提供偏移量）
- 访问普通数据时，使用DS:偏移量
- 访问栈数据时，使用SS:SP/BP

看到这里，你可能会说，代码段使用CS存储段选择符，数据段使用DS存储段选择符，栈使用SS存储段选择符，那么，BSS段和堆使用哪个寄存器存储段选择符呢？在分段机制下，.data、.bss、堆通常会被映射到一块连续的物理内存中，因此，它们共享同一个段描述符，也就是都是用DS存储这个段描述符。

这里我们在补充讲解一下堆栈。堆和栈是程序中需要动态增长的部分。每次函数调用都会压入新的栈帧，栈向下增长。调用malloc()或new时，堆向上增长。既然空间大小是不固定的，那么，段界限初始设置为多大？

在分段系统中，这确实是个挑战。操作系统通常有两种策略：
- 固定大小策略：为堆段和栈段分配一个固定的、预期足够的大小。比如，栈段设为8MB，堆段设为16MB。这简单但不够灵活：太小可能导致溢出，太大则浪费内存。
- 动态调整策略（更复杂）：初始设置较小的段界限，当程序访问超出当前界限时，触发段越界异常。每个段映射到物理内存中必须是连续的。要扩展一个段，可能需要将它复制到一个更大的连续空间，这很耗时。而且，频繁调整段大小会加剧内存碎片化。

正因为这些限制，现代操作系统虽然保留了段的概念（为了兼容性和基础保护），但真正的内存管理交给了分页机制。**分页使用固定大小的页作为管理单位，完美解决了动态增长和碎片化问题**。这一部分在下一节中详细讲解。

除此之外，当物理内存不足时，操作系统需要将一些暂时不用的数据“换出”到磁盘，腾出空间，即后面要讲到的页面置换。分段的基本交换单位是整个“段”。想象一下，一个进程的数据段可能非常大（几百MB），但其中可能只有一小部分近期被使用过。然而，在分段机制下，一旦决定换出这个数据段，就必须把整个几百MB的数据全部写入磁盘。同样，换入时也需要全部读回。这种粗粒度的交换导致巨大的、不必要的磁盘I/O开销，严重拖慢系统性能。

## 分页机制
分段机制有两个主要问题：内存碎片和低效的页面置换。为了解决这两个问题，发明了新的映射规则：分页机制，从此分页替代分段，成了现代操作系统主流的内存管理方式。

分段机制按照段来进行虚拟内存到物理内存的映射，因为段（比如堆栈）会动态增长，大小并不固定，就会涉及段空间的重新分配，导致内存碎片，另外，段（比如堆）大小可能很大，按照段来进行页面置换（内存不足时），就会导致大量数据的换入换出（内存和磁盘之间）。

对比分段，分页采用一个完全不同的内存映射方法。**它将虚拟内存划分为一个个大小相同的页（Page），一般一页大小为4KB，同样，它将物理内存划分成一个个大小相同的页，物理页的大小一般跟虚拟页的大小一致**。内存映射的基本单位，从“段”变成了“页”。在内存映射层面，不再有“段”的概念。

那么，现在的问题是，怎么维护一个进程的虚拟页跟物理页的映射关系呢？这就是通过页表来完成。

操作系统为每个进程维护一个页表，页表存储在内存中，页表在内存中的起始地址（即页表的基地址）存储在进程的PCB中，当进程切换时，页表的基地址会写入页基址寄存器（如x86的CR3），后续MMU就可以通过页基址寄存器找到页表，然后再进行内存地址的翻译。

那么，页表具体长什么样子呢？

我们可以将页表想象成一个大的数组，每个数组的下标是虚拟页号，数组的元素（即页表项）是这个虚拟页号对应的物理页号。当然，如果这个虚拟页号对应的虚拟页没有被使用（程序并不会使用所有的虚拟内存，只是使用一部分，但是，页表是针对整个虚拟内存构建的），那么，页表项中就不会记录它对应的物理页号。

对于32位操作系统，其虚拟内存大小是4GB，因为一页大小是4KB，所以，总共就有4GB/4KB=2^20个虚拟页，对应的虚拟页号是0~2^20-1，物理页号也是如此编码，范围不会超过虚拟页号（因为物理内存大于虚拟内存之后，多出来的是用不上的）。那么，也就是说，对于32位操作系统来说，页表项用来记录物理页号的部分只需要20个二进制位。当然，页表项还需要记录其他信息，因此，一个页表项大小是4字节（即32bits）。当然，对于64位操作系统，物理页号范围更大，需要更多的二进制位记录，因此，页表项大小一般是8字节。

除了物理页号，页表项中还记录了其他信息，详细如下所示。其中比较重要的几个信息是：
- 有效位：此映射是否有效？值为1表示该页已映射到物理内存；值为0表示该页未映射（可能从未使用，或因内存不足被页面置换到磁盘上）。当进程访问有效位为0的页时，MMU触发缺页异常，操作系统介入处理。这允许操作系统惰性分配物理内存：只有真正访问的虚拟页才分配物理页。
- 保护位：可读/可写/可执行？
- 访问位：近期是否被访问过？（用于页面置换算法）
- 脏位：内容是否被修改过？（页面置换被换出时，被修改过的页需要写回磁盘）。

通过页表结构来看，分页解决了分段的两个痛点：
* 内存碎片：因为内存分配的单位是比较小的页（仅4KB），基本不会出现像分段机制中出现的“总空间够但找不到连续块“的情况
* 低效交换：当需要页面置换时，操作系统可以精准地换出哪些最近最小使用的个别页，而不是动辄换出整个大数据段，IO开销大幅降低

## 页面置换
当一个进程需要访问某个虚拟页时，才会给这个虚拟页在页表中映射一个物理页，然后把数据实实在在的加载到这个物理页，但是如果所有的物理页都被使用了，没有可用的物理页去分配给这个虚拟页，进程没法存放数据了，这个时候该怎么办呢？

这就需要页面置换，将临时用不到的物理页中的数据写回磁盘，腾出物理页给这个进程使用。**页面置换是解决有限的物理内存与无限的内存需求（多进程并发运行）这一矛盾的主要手段**。虽然页面置换的核心思想非常简单，有点类似缓存淘汰，但实现细节稍有繁琐，比如选择哪个物理页换出？换出到哪里？从哪里加载数据到物理页？等等

当一个进程被创建后，会为其虚拟内存创建页表，最初页表中的大多数页表项的有效位都设置为0，表示这些虚拟页还没有对应的物理内存。

程序经过编译之后，会以某种格式存储在磁盘中，叫做可执行文件。可执行文件中包含好几个段：代码段、数据段、BSS段，堆栈中的内容是在程序执行中动态生成的，一般不包括在可执行文件中。

当进程访问到某个虚拟页时，才对其进行分配物理页，并从磁盘加载内容。这就是所谓的惰性分配。这种惰性分配策略有几个关键优势：其一是启动速度快，进程可以快速启动，不需要等待所有代码和数据加载完毕；其二是节省内存，只有真正被访问的页面才占用物理内存。

按照是否需要从磁盘的可执行文件中加载内容，我们把虚拟页分为两类：文件映射页和匿名页。其中，代码段、数据段对应的虚拟页都是文件映射页。BSS段、堆、栈对应的虚拟页都是匿名页。
- 对于文件映射页，对应的物理页需要换出（swap out）时，直接将对应的页表项的有效位设置为0，然后将页表项中的物理页号替换成数据在磁盘中的位置，等待下次进程访问这个虚拟页时，能够从磁盘中加载数据到物理页。
- 对于匿名页，对应的物理页需要换出时，需要将物理页中的数据写入交换区（swap），并在页表项中记录数据在交换区的位置，以便进程需要访问这个虚拟页的时候，能够从交换区加载到对应的数据。

**交换区是磁盘上的一块特殊区域，专门用于存储被换出的内存页**。交换区被划分为与物理页大小相同的交换槽（通常4KB）。操作系统维护一个数据结构（如位图）来跟踪哪些交换槽是空闲的。当一个匿名页被换出时，操作系统在交换区分配一个空闲槽，将页内容写入该槽。

**交换区的大小没有统一的标准。如果物理内存足够大（比如16GB以上），可以设置较小的交换区（2GB左右）甚至不设置交换区。相反，如果物理内存不大（比如4GB、8GB等），交换区大小设置为物理内存的1到2倍。当物理内存和交换区都耗尽时，操作系统将无法继续分配内存，可能导致进程被杀死**。

当CPU访问一个虚拟地址，MMU查找页表后发现其对应的页表项有效位为0。这意味着该页不在物理内存中。这个时候，CPU有可能工作在用户态，怎么才能切换到内核态，让操作系统内核去帮忙加载对应的物理页呢？这就要用到我们在讲解「系统调用」那一节课时，提到的一个重要的机制：异常。

当MMU发现页表项的有效位为0时，会立即报告一个缺页异常。CPU暂停当前进程，切换到内核模式。操作系统的缺页异常处理程序开始工作：
- STEP 1：查找空闲物理页。检查是否有空闲的物理页。如果有，跳到第4步。
- STEP 2：选择置换物理页。如果没有空闲页框，页面置换算法被激活。算法根据某种规则，从当前所有正在使用的物理页中，挑选出一个“牺牲者”。
- STEP 3：写出牺牲页swap out。检查牺牲页的“脏位”。如果为1（内容被修改过），必须将其内容写回磁盘（交换区）。如果为0（内容没有被修改），因其磁盘上有副本，直接丢弃即可。
- STEP 4：读入目标页swap in。从磁盘（可能是可执行文件或交换区）将引发缺页的那个页读入到腾出的（或找到的空闲）物理页中。
- STEP 5：更新页表。修改页表项，将有效位置1，并填入新的物理页框号。
- STEP 6：重启执行指令。CPU从导致缺页的指令重新开始执行。进程浑然不觉地继续运行。

整个过程，步骤3和4是性能的核心瓶颈，因为它们涉及缓慢的磁盘I/O。但是，第2步却是整个过程的关键。一个好的置换算法，能够挑选出最合理的需要换出的物理页，最小化未来发生缺页的次数。

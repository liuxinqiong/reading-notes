## 系统概述
计算机的IO设备众多，比如键盘、鼠标、磁盘等熟知的设备，还有一些通过usb接口等即插即用的各种设备，比如摄像头、麦克风等等，面对如此多样的设备，操作系统采用了分类管理的方法，根据设备类型将其分为几大类

块设备 Block Device，以固定大小的数据块为单位进行读写操作，典型代表是硬盘、固态硬盘、U盘等存储设备。块设备的特点包括：
* 支持随机访问：可以直接跳到任意位置读写数据
* 数据以块为单位：通常块大小为512字节或4KB
* 通常缓存机制

字符设备 Character Device，以字符流的形式进行数据传输，没有固定的块大小，典型代表是键盘、鼠标、打印机等，字符设备的特点包括
* 顺序访问：数据通常按到达顺序处理
* 可变长度：数据单位大小不固定
* 实时性要求：许多字符设备需要及时响应

网络设备（Network Device）是特殊的I/O设备，它不属于传统的块设备或字符设备分类。网络设备通过数据包的形式传输信息，每个数据包都有源地址、目标地址和数据内容。

网络通信的复杂性在于它的异步性和不可靠性。与文件读写不同，网络数据可能丢失、重复、乱序到达，因此需要专门的协议栈（如TCP/IP）来处理这些问题。网络设备就像是一个国际邮递系统，不仅需要传输信件，还需要处理地址解析、路由选择、错误恢复等一系列复杂问题。

操作系统通过设备驱动程序来管理这些多样性。驱动程序是设备和操作系统之间的翻译官，它将操作系统的通用I/O请求翻译成特定设备能理解的命令。这种设计的精妙之处在于：应用程序开发者不需要了解设备细节，设备制造商只需要提供符合标准接口的驱动程序。

IO控制
* 程序控制IO：早期的控制方式，也称为轮训或忙等待，这种方式的原理很简单，CPU不断的询问设备“你准备好了吗？”，直到设备回答”准备好了“，然后CPU才开始数据传输。优点是不需要特殊的硬件支持，但缺点显而易见，CPU时间被极大的浪费了
* 中断驱动IO：设备在准备好数据传输时，会主动打断CPU当前的工作，请求CPU处理IO操作。优势是提高的CPU的利用率，代价是：每次中断都需要保存和恢复CPU状态，这开销在小数据量传输时可能得不偿失。
* 直接内存访问 DMA：是一个专门的硬件，独立于CPU在设备和内存之间传输数据，CPU只需要告诉DMA控制器：把设备A上的数据传到内存地址X到Y的区域，然后就可以做其他工作，DMA控制器会自行完成整个传输过程，完成后通过中断通知CPU。

如果说I/O设备的多样性给操作系统带来了管理上的挑战，那么“一切皆文件”（Everything is a file）这一哲学思想就是解决这一挑战的优雅方案。这是Unix及其后继系统（如Linux）的核心设计理念。

什么是“一切皆文件”？简单说，就是用操作文件的方式来操作一切I/O设备。无论你是在读取硬盘上的文档、从键盘获取输入、向显示器输出图像，还是进行网络通信，都可以使用相同或相似的接口（open、read、write、close等）。

操作系统在文件系统之上，又抽象了一层虚拟文件系统（VFS），这才是实现“一切皆文件”的关键技术。VFS是内核中的一个软件层，它为应用程序提供了一个统一的文件操作接口，同时向下支持多种具体的文件系统（如ext4、NTFS、FAT32）和各类I/O设备。

传统文件系统（如ext4、NTFS）主要管理磁盘存储设备。它们负责将文件数据组织成块，管理空闲空间，维护目录结构等。然而，操作系统通过设备文件的机制，将其他类型的I/O设备也纳入文件框架中。

设备文件是位于/dev目录下的特殊文件，它们不占用磁盘空间，而是作为设备驱动程序的接口。设备文件的创建和管理由操作系统负责。当内核检测到新设备时，会根据设备类型和驱动程序信息，在/dev目录下创建设备文件节点。这些节点包含了设备的主设备号和次设备号：
- 主设备号：标识设备类型，对应特定的驱动程序
- 次设备号：标识同一驱动程序管理的不同设备实例

设备文件本身不存储数据，它们只是访问设备的入口。当你对设备文件进行操作时，VFS会将操作重定向到相应的设备驱动程序。

总结一下就是：
- 真正的文件系统（如ext4）管理磁盘空间
- 设备文件提供访问设备的接口，但它们不存储数据
- 虚拟文件系统作为中间层，统一处理普通文件和设备文件

典型的IO子系统可以分为5层，从用户空间到硬件层面，形成一个完整的处理流水线
* 用户空间IO库：如C语言的stdio或C++的iostream，目的是提供友好、易用的编程接口
* 系统调用接口：用户空间和内核空间的边界，当应用程序调用如read/write这样的函数时，会触发系统调用，从用户模式切换到内核模式
* 虚拟文件系统：I负责将通用的IO请求路由到具体的处理模块，对于文件操作，请求被转发给文件桶，对于设备操作，请求被转发给相应的设备驱动程序
* 设备驱动程序：操作系统中最了解特定设备的部分，每个驱动程序都是设备和操作系统之间的翻译官，将通用的IO请求转换为设备能理解的命令
* 中断处理程序：最接近硬件的一层，当中断发生时，CPU会立即暂停当前工作，跳转到中断处理程序

## IO模型
IO模型是操作系统提供给应用程序的一种抽象，定义了应用程序如何发起和处理IO操作，正则正确的IO模型对于构建高性能、高并发的应用程序至关重要。

同步阻塞IO：最简单、最直观的IO模型，当程序发起一个IO操作，它会一直等待，直到数据准备好并被复制到了应用程序的缓冲区，在这个等待过程中，应用程序什么也做不了，就像被阻塞了一样。
* 符合人类的线性思维，习惯按照顺序做事
* 不需要考虑并发，不需要管理状态机，代码写起来直观易懂
* 效率低下，应用等待IO完成时，不能做任何其他事情，**对于交互式应用，意味着页面会冻结，对于服务器应用，意味着每个连接都需要一个单独的线程或进程，造成资源浪费**。

同步非阻塞IO：对阻塞IO的一种改进，在这种模型下，当应用程序发起IO操作时，如果数据没有就绪，系统调用会立即返回一个错误码，而不是阻塞等待。应用程序需要反复尝试，直到数据就绪。

IO多路复用
* 允许应用程序同时监控多个文件描述符，当其中任何一个就绪时，应用程序就会得到通知，这样一个线程可以处理多个IO操作。常见的多路复用系统调用有 select, poll, epoll
* 核心思想史集中管理多个 IO 操作，不需要为每个 IO 操作分配一个线程，也不需要不断的轮训每个操作是否完成。这种模型特别适合高并发的服务器应用

信号驱动IO
* 允许应用程序在发起IO操作后继续执行，当数据就绪时，内核会发送一个信号通知应用程序
* 是真正的事件驱动模型，应用程序不需要轮训，也不需要阻塞等待。这种模型听起来很完美，但它并没有成为主流的IO模型，原因在于信号的不可靠性和编程复杂性。在多线程环境中，信号的处理更加复杂，而且当有大量IO操作时，信号可能会频繁到达，严重影响应用程序的性能

异步IO
* 最先进的IO模型，应用程序发起IO操作后立即返回，不需要等待数据就绪，当整个IO操作（包括数据从内核复制到用户空间）完成后，内核会通知应用程序
* 与信号驱动IO不同，信号驱动IO在数据就绪时通知，应用程序还需要自己读取数据，而异步IO在整个操作完成后才通知。

让我们通过一个生活中的比喻来总结五种I/O模型：
- 同步阻塞I/O： 你去餐厅点餐，然后坐在座位上等待，直到服务员把菜端上来。期间你不能离开座位。
- 同步非阻塞I/O： 你不断去厨房门口询问：“我的菜好了吗？”如果没好，你就回去做点别的事，过一会儿再来问。
- I/O多路复用： 你请了一个助手，让他同时监控多个餐厅的做菜进度。当任何一家餐厅的菜好了，助手就通知你。
- 信号驱动I/O： 你告诉餐厅：“我的菜好了就给我打电话。”然后你可以去做其他事情。菜好时，餐厅会打电话通知你。
- 异步I/O： 你告诉餐厅：“帮我点一份餐，做好后送到我家，放进冰箱，然后发短信告诉我。”你完全不需要等待，可以做任何事，直到收到短信通知。

## 多路复用
在现代互联网应用中，一个服务器可能需要同时处理数万个甚至数十万个并发连接。如果为每个连接创建一个线程或进程，系统资源很快就会被耗尽。IO多路复用计数应运而生，它让单个线程能够同时监控和处理多个IO操作，成为构建高并发系统的基石。

在大多数网络应用中，CPU等待IO的时间远远超过实际计算的时间，当一个Web服务器处理HTTP请求时，它需要
* 接收客户端请求（网络IO）
* 可能读取磁盘文件（磁盘IO）
* 可能查询数据库（网络和磁盘IO）
* 向客户端发送响应（网络IO）

在整个过程中，CPU真正执行代码的时间，可能只占整个请求处理时间的1%甚至更少，其余99%的时间都在等待各种I/O操作完成。如果采用传统的“一线程一连接”模型，每个线程在等待I/O时会被阻塞，操作系统会切换到其他线程。当连接数达到数千时，线程间的上下文切换开销变得不可接受。更糟糕的是，每个线程都需要自己的栈空间（通常至少1MB），内存消耗也会成为问题。

多路复用的本质是一种观察者模式在操作系统层面的实现。应用程序不再是主动轮询每个I/O设备的状态，因为这样效率很低，而是告诉操作系统：“这里有一组I/O操作，当其中任何一个就绪时，请通知我。”

这种模式转变带来了几个关键优势：
- 资源效率：一个线程可以管理大量连接
- 响应速度：当I/O就绪时能立即处理，无需等待轮询
- 可扩展性：连接数的增加不会线性增加线程数

select 模型，1983年引入，应用程序提供一个文件描述符集合，操作系统会监控这些描述符，当其中任何一个就绪时返回

当应用程序调用 select 时，操作系统内核会
* 将用户空间的位图复制到内核空间
* 遍历位图中所有被设置为1的位置
* 检查对应的文件描述符是否就绪
* 修改位图，将就绪的描述符对应的位设置为1

存在的问题
* 线性扫描的开销：每次调用 select 内核都需要遍历整个位图，检查每个被监控的文件描述符
* 重复的数据拷贝：每次调用 select 都需要在用户空间和内核空间复制位图
* 位图大小的限制：select 使用固定大小的位图，通常是 1024 位，意味着最多只能监控 1024 个文件描述符

poll 模型和 select 类似，只是存储 fd 集合的方式不同，poll 使用 pollfd 结构（链表）而非 select 的 fd_set 结构（位图）。在内部处理流程上，它们基本是一致的，也是需要进行轮训查找就绪的 fd。不过因为 poll 基于链表存储 fd，所以无最大文件描述符限制，但并未从根本上解决 select 存在的问题。

epoll 模型在 Linux 2.5中引入（2002年），跟 select 和 poll 不同，epoll 的多路复用实现思想发生了根本转变。

epoll主要有三个系统调用：
- epoll_create：创建一个epoll实例
- epoll_ctl：向epoll实例添加、修改或删除文件描述符。
- epoll_wait：等待事件发生

也就是说，epoll提供了系统调用来直接操作（添加、删除、修改）内核空间维护的fd集合，不用像select和poll那样每次从用户空间拷贝完整的fd集合到内核空间。

epoll的实现依赖于两个数据结构：
- 红黑树：用于高效管理所有被监控的文件描述符。红黑树是一种自平衡的二叉查找树，插入、删除和查找操作的时间复杂度都是O(log N)。当应用程序通过epoll_ctl添加文件描述符时，内核将其插入红黑树；当文件描述符关闭时，内核将其从红黑树中删除。
- 就绪列表：一个双向链表，用于存储所有就绪的文件描述符。当I/O事件发生时，设备驱动程序会调用回调函数，将对应的文件描述符添加到就绪列表中。当应用程序调用epoll_wait时，内核只需遍历这个就绪列表，将事件返回给应用程序。

以上示例展示了epoll的几个关键特性：
- 一次设置，多次使用：监听套接字只需添加一次，之后不需要重复操作
- 只返回就绪的事件：epoll_wait只返回实际发生事件的文件描述符
- 边缘触发模式：通过EPOLLET标志启用，只在状态变化时通知

实际上，epoll支持两种事件通知模式：
- 水平触发（Level-Triggered，LT）：默认模式。只要文件描述符处于就绪状态（例如，接收缓冲区中有数据），每次调用epoll_wait都会报告该事件。这与select/poll的行为一致。
- 边缘触发（Edge-Triggered，ET）：只在状态变化时报告事件。例如，当接收缓冲区从空变为非空时，会报告一次EPOLLIN事件。之后即使缓冲区中还有数据，也不会再次报告，除非应用程序读取了部分数据后，缓冲区又从空变为非空。

ET模式的优势在于减少了系统调用次数，但ET模式需要应用程序更加小心地处理I/O。在LT模式下，如果应用程序没有读取所有数据，下次epoll_wait会再次报告该文件描述符就绪，而在ET模式下，只有在新的数据到达时才会再次报告，就有可能导致部分数据迟迟不被读取。

## 异步IO
阻塞、非阻塞、同步、异步这几个概念之间的区别和联系，阻塞和非阻塞关注的是调用者在等待期间是否可以做其他事情。同步和异步关注的结果的获取方式，即调用者是否主动等待或者询问结果，还是由系统来通知。
* 阻塞：调用在结果返回之前会挂起调用线程，直到操作完成
* 非阻塞：调用立即返回，如果操作不能立即完成，返回错误或部分结果
* 同步：调用者主动等待操作完成，即调用者必须检查或等待结果
* 异步：调用者发起操作后可以继续做其他事，操作完成后通过某种机制通知调用者

select、poll、epoll等机制本质上是一种阻塞在多个文件描述符上的同步I/O模型：
- 进程调用select阻塞等待，直到监控的多个文件描述符中至少有一个数据就绪。
- select返回后，进程再调用read从就绪的描述符读取数据。这个read调用是同步阻塞的（数据拷贝阶段阻塞）。

因此，多路复用并没有改变I/O本身的同步性质，它只是用一个线程同时监控多个I/O操作，减少了线程数量。调用者需要等待结果（等待在select上），因此，它也是同步I/O。

真正的异步I/O模型（如Linux AIO）的处理流程如下：
- 应用程序调用aio_read，传入用户缓冲区地址，然后立即返回。
- 内核负责等待数据就绪，并将数据从内核直接拷贝到用户缓冲区。
- 当整个操作（包括数据拷贝）完成后，内核通过某种方式（信号、回调、完成队列）通知应用程序。

在异步I/O中，应用程序既不阻塞在数据准备阶段，也不阻塞在数据拷贝阶段。数据拷贝是由内核替应用程序完成的。调用者进程也不需要等待结果或者轮询结果，操作系统内核会在所有I/O操作都完成之后，通知调用者。因此，这才是妥妥的异步。

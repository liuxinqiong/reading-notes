## HTTP
所谓应用层协议就是各个应用自己定义的数据格式和交互规则。比较经典的一些应用层协议包括：HTTP、HTTPS、DNS、FTP、POP3/SMTP等。当然你也可以为自己的应用定义自己的应用层协议，比如Dubbo、Thrift等RPC框架、Kafka、RocketMQ等中间件框架，Redis、MySQL等，都有定义自己的应用层协议，用户客户端与服务器之间的数据交互。

HTTP四部曲：HTTP1.0、HTTP1.1、HTTP2.0、HTTP3.0
* HTTP1.0：非持久连接，每个HTTP请求都需要建立一个新的TCP连接
* HTTP1.1：引入了持久连接，默认开启，解决了短连接问题，但仍然不完美，存在队列阻塞
* HTTP2.0：二进制分帧、多路复用、头部压缩、服务器推送

当然，长连接也不会永远保持。长连接通常由双方（客户端或服务器）根据一些规则来关闭：
* 超时：这是最常见的断开原因。服务器端一般会设置一个保持超时（keep-alive timeout），例如60秒。如果在这段时间内，这条连接上没有新的请求，服务器就会主动关闭连接，以释放资源。
* 最大请求数：有些服务器会限制一条长连接上能处理的最大请求数量（例如100个）。超过这个数量后，服务器会在响应中加上 Connection: close 头部，通知客户端在处理完最后一个请求后关闭连接。
* 客户端主动关闭：当用户关闭浏览器标签页或导航到其他网站时，浏览器会主动关闭原先的TCP连接。
* 服务器端主动关闭：当服务器负载过高、重启或遇到错误时，也可能强制关闭空闲或正在使用的连接。
* 网络环境变化：例如移动网络切换、Wi-Fi断开等，都可能导致底层TCP连接中断。

队头阻塞

HTTP/1.1 的持久连接虽然允许在同一个连接上发送多个请求，但这些请求必须是串行的。也就是说，你必须先收到第一个请求的响应，才能发出第二个请求。这就是著名的队头阻塞（Head-of-Line Blocking，简称 HOL）问题。

后来协议设计者尝试引入“管道化”（Pipelining）机制来尝试缓解这个问题。它允许客户端在收到上一个响应之前，就连续发送多个请求。听起来不错，对吧？但问题在于，服务器端在处理响应时，依然需要按照发送请求的先后顺序返回响应。如果第一个请求处理的动态页面很慢（比如查询复杂的数据库），即使第二个请求只是一个读取静态 1.jpg 图片的快速请求，它也必须在服务器端等待第一个请求处理完并返回后，才能被返回。

那为何响应要按照请求的顺序依次来发送呢？哪个请求处理完了就发送哪个请求的响应不行吗？

HTTP1.1 之所以要求响应必须按序返回，问题在于HTTP1.1中，请求和响应之间没有任何明确的标识符来建议一一对应的关系。在一个TCP连接上，客户端连续发送了多个请求，服务端收到这些请求后，可以并行处理它们，但是当服务器准备发送响应时，它面临一个难题：它发出的响应，客户端该如何知道这个响应对应的是哪个请求？因此客户端只能依靠一个简单的规则来匹配：响应的返回顺序必须与请求的发送顺序完全一致。

**为了在浏览器端突破“一个连接只能串行请求”的限制，开发者们想出了一个“土办法”：为同一个域名建立多个 TCP 连接**。浏览器通常允许对同一个域名开启 6～8 个 TCP 连接。这相当于在超市里开了 6～8 个收银台，可以同时处理 6～8 个请求，极大地缓解了队头阻塞问题。

因此，尽管 HTTP/1.1 存在队头阻塞问题，但凭借其出色的兼容性和并发连接机制，服务了我们长达十六年之久。直到今天，很多旧的系统或配置仍在运行 HTTP/1.1。这里解释一下，HTTP/1.1 的兼容性主要体现在：当一个 HTTP/1.1 的客户端与一个仅支持 HTTP/1.0 的古老服务器通信时，它可以自动降级，使用 HTTP/1.0 的语法和语义进行交互。反之，HTTP/1.1 服务器也能正确处理来自 HTTP/1.0 客户端的请求。

随着网页越来越复杂，HTTP1.1的**一个连接串行请求**的模式已经捉襟见肘，谷歌公司退出SPDY协议，尝试解决这个问题，HTTP2.0就是在SPDY的基础上演化而来的标准。

二进制分帧（Binary Framing）

HTTP/2.0 最大的变革，是将 HTTP/1.0 的文本协议升级为二进制协议。但这不仅仅是“从文本变成二进制”这么简单，它引入了一个位于 Socket 接口与应用层 HTTP 语义之间的新的抽象层：二进制分帧层。

在 HTTP/2.0 中，数据被拆分成更小的帧（Frame）。帧是 HTTP/2.0 中最小的数据传输单位，它包含了长度、类型、标志、流标识符以及载荷（payload）。
* 流标识符（Stream ID）：这是整个设计的灵魂。每个请求或响应都会被分配一个唯一的流 ID。
* 帧（Frame）：不同类型的帧承载不同数据。例如，HEADERS 帧用来传输头部，DATA 帧用来传输内容体。

一个完整的请求或响应，被拆分成多个帧（一个 HEADERS 帧加 N 个 DATA 帧），这些帧属于同一个流，都带着相同的流标识符。然后，这些帧可以被乱序地交错发送（即多路复用），接收方再根据流标识符将它们重新组装起来。

多路复用：一个请求都能被分成多个帧交错发送了，而多个请求之间交错发送也是可以的，这正是解决队列阻塞的核心方法。这个设计的精髓在于：用显示的标识符（流ID）取代了隐式的顺序依赖，是的请求和响应的关联不再依赖于传输顺序，从而实现真正的多路复用。

头部压缩（HPACK）

在 HTTP/1.1 协议中，每个 TCP 连接在发送 HTTP 请求时，都会带上重复的、庞大的头部信息。比如，每个请求都有几乎一样的 Host、User-Agent、Accept、Cookie 等头部。这些头部信息动辄几百字节甚至上千字节，而且都是以明文文本形式传输的。如果请求一个网页，需要加载 100 个资源（HTML、CSS、JS、图片等），那么仅仅是重复传输这些头部，就会产生巨大的开销。

为了解决头部冗余的问题，HTTP/2.0 采用了专门的 HPACK 算法对头部进行压缩。这个算法的精妙之处在于，它同时在客户端和服务器端维护一个静态字典和一个动态字典。
* 静态字典：预定义了常见的头部键值对，比如 :method: GET 对应一个索引值。传输时只需要发送这个索引号，而不是完整的字符串 :method: GET。
* 动态字典：在连接过程中动态更新。双方可以将之前发送过的、重复出现的自定义头部（如 Cookie 或 User-Agent）添加到字典中，后续再发送相同的头部时，只需要发送对应的索引号即可。

这样一来，每次请求的头部内容在网络上传输的体积，也会被压缩到极致，大大减少了带宽占用和传输延迟。

服务器推送（Server Push）

在 HTTP/1.1 时代，浏览器解析 HTML 时，发现需要 style.css 和 script.js，才会再次发起请求去获取它们。HTTP/2.0 协议支持服务器推送，允许服务器在解析到 HTML 请求时，就主动预测客户端接下来会需要的资源（如 CSS、JS），并提前将这些资源推送到客户端的缓存中。当浏览器解析完 HTML，真正需要这些资源时，它们已经静静地躺在客户端缓存里了。

HTTP3.0 QUIC协议

虽然HTTP2.0完美解决了应用层的队头阻塞，但它依然运行在TCP协议之上。而TCP协议本身，也有自己的队头阻塞。

在 HTTP/2.0 里，虽然多个请求是并行发送、处理、返回响应的，**但在 TCP 层看来，它们都是同一个连接上的字节流。只要一个包丢了，所有流的传输都会被暂停，直到那个包被重传回来**。这就是 TCP 层的队头阻塞。这个问题在移动网络等高丢包率的网络环境下尤其严重。一个丢包就可能让整个连接上的所有请求都陷入等待，性能急剧下降。

为了解决 TCP 的队头阻塞问题，HTTP/3.0 做了一件非常重大的改造：**彻底放弃 TCP，转而基于 UDP 协议来实现**。我们知道 UDP 是无连接、不可靠的协议，纯粹地依赖 UDP 实现 HTTP 协议，显然是不可能的。因此，HTTP/3.0 在 UDP 之上实现了全新的 QUIC（Quick UDP Internet Connections，快速 UDP 互联网连接协议）。可以理解为是在 UDP 之上，实现了一个“特殊版本的 TCP”。

QUIC 在 UDP 之上，自己实现了类似于 HTTP/2.0 的“多路复用”机制。不同流之间的数据传输是完全独立的。**每个流都有自己的序列号，用于保证该流内部的可靠性和有序性。不同流之间的数据独立编号，互不干扰。当某个流（一个请求或响应成为一个流）的一个数据包丢失时，QUIC 只会在该流上暂停等待重传，而其他流的包可以继续正常接收和处理**。接收方收到其他流的包后，会直接将其重组并交给应用层，完全不受丢失包的影响。

除此之外，QUIC 还解决了连接迁移问题。传统的 TCP 连接依赖于源 IP 和端口，当用户从 Wi-Fi 切换到移动网络时，IP 变化会导致连接中断，需要重新握手建立连接。而 QUIC 使用连接 ID 来标识一条连接，即使网络发生变化，只要连接 ID 不变，连接就能无缝迁移，移动体验大幅提升。

回顾 HTTP 的演进史，每一代协议的变革，都是为了解决上一代最核心的性能瓶颈
* HTTP1.0 定义了基本形态，但短连接是痛点
* HTTP1.1 用长连接解决了连接开销，但又引入了队头阻塞
* HTTP2.0 用多路复用解决了队头阻塞，但受限于TCP层的固有问题
* HTTP3.0 用基于UDP的QUIC协议，彻底重构了传输层，从根本解决了队头阻塞和连接迁移等问题

## HTTPS
HTTP协议的三个核心安全问题：窃听、篡改、冒充。为了解决这些问题，HTTPS应运而生，他并非全新的协议，而是在HTTP的基础上，增加了一层由TLS（传输层安全协议）提供的安全机制。

安全场景距离
* 比如同一个网络中，可以通过网络分析工具，捕获你数据包中的数据，这就是窃听
* 你网络下载的软件安装包，攻击者在传输过程中截获了这个文件，植入了一段恶意代码，然后再转发给你的电脑，这就是篡改
* 打开电商网站，但你的DNS请求被劫持，你访问的网站是由攻击者精心搭建的冒牌货，此时你输入了账号密码，这些信息瞬间落入骗子手中，这就是冒充

HTTP的三大缺陷：信息传输不加密（导致窃听）、没有完整性校验（导致篡改）、无法验证通信方身份（导致冒充）。

解决窃听问题：信息加密。

既然对称加密速度快但存在密钥分发难题，而非对称加密能安全分发密钥但速度慢，那么自然想到将两者结合起来，取长补短。

混合加密的基本思想是：
* 使用非对称加密安全地传输一个临时的对称密钥（称为会话密钥）。
* 一旦双方都拥有了这个会话密钥，后续的所有通信数据都使用对称加密进行加解密，以获得高性能。

整个流程如下：
* 服务器生成一对密钥：公钥和私钥。私钥由服务器妥善保管，绝不泄露。
* 服务器将公钥发送给客户端。这个发送过程是明文的，因为公钥本身不需要保密。
* 客户端生成一个对称密钥（称为会话密钥），使用服务器的公钥对其进行加密，得到密文。
* 客户端将密文发送给服务器。
* 服务器收到密文后，使用自己的私钥解密，得到会话密钥。
* 双方使用会话密钥（对称加密算法）加密所有数据再进行传输。

混合加密既保证了密钥分发的安全性（借助非对称加密），又保障了大数据量传输的效率（借助对称加密）。然而，混合加密机制仍然存在一个关键问题：客户端如何确认自己收到的公钥确实属于目标服务器？

如果攻击者在第一步就拦截了服务器的公钥，并替换成自己的公钥，那么后续所有加密都将被攻击者掌控。客户端会用攻击者的公钥加密会话密钥，攻击者用自己的私钥解密后就能获取会话密钥，然后他再用真正的服务器公钥重新加密会话密钥发送给服务器，从而在中间窃听和篡改所有通信。这正是我们前面提到的“冒充”问题，也是著名的中间人攻击。

解决冒充问题：身份验证

在现实世界中，我们靠什么来证明“我是谁”？靠身份证。身份证由国家权威机构（公安局）签发，上面有你的照片、姓名等关键信息，并有公安机关的印章。任何机构（比如银行、酒店）只要信任国家这个权威，看到这张身份证，就能确认你的身份。

在网络世界里，扮演这个权威角色的就是 CA，全称是证书颁发机构（Certificate Authority）。CA 是受浏览器和操作系统厂商信任的第三方机构，比如著名的 GlobalSign、DigiCert、Let's Encrypt 等。浏览器和操作系统中会预置一批根 CA 的证书（包含它们的公钥）。

而扮演“身份证”角色的就是数字证书。数字证书是由权威的 CA 签发的电子文档，用于证明某个公钥确实属于某个实体（如域名）。证书中通常包含以下信息：
* 主体的信息
* 主体的公钥
* 证书签发者（CA）的信息
* 证书的有效期
* 签发者的数字签名

数字证书的颁发过程
* 提交申请材料：网站管理员把自己的公钥，以及一些网站的身份信息（如域名、公司名称等）提交给CA
* CA审核：CA会通过各种方式核实这些信息的真实性，比如通过云服务商、DNS等，确认你确实应该这个域名的管理权
* 签发证书：审核通过后，CA会将这些信息打包在一起，形成一个文件。CA使用哈希算法对文件内容计算摘要，然后用自己的私钥对摘要进行签名（数字签名是非对称加密的另一种应用），生成一个独一无二的数字签名，一并放入这个文件，最终就形成了数字证书

数字签名的验证过程：
1. 客户端（浏览器）从证书中提取签发该证书的 CA 的信息，并查找本地是否内置该 CA 的根证书（包含 CA 的公钥）。如果找不到，则验证失败（浏览器会提示“证书颁发机构不受信任”）。
2. 如果找到了对应的 CA 公钥，客户端使用该公钥验证证书末尾的数字签名，得到一段摘要 A。
3. 客户端使用证书中描述的哈希算法（如 SHA-256）对证书的内容（除签名外的部分）重新计算摘要，得到摘要 B。
4. 客户端比较摘要 A 和摘要 B。如果两者一致，则证明：
5. 证书内容没有被篡改（因为任何改动都会导致摘要 B 变化）。
6. 证书确实是由该 CA 签发的（因为只有拥有 CA 私钥的一方才能生成有效签名）。
7. 此外，客户端还会验证证书的有效期是否在有效期内、证书的域名是否与正在访问的域名一致、证书是否被吊销等。
8. 如果所有验证都通过，客户端就信任该证书，并从中提取服务器的公钥，这个公钥就是 HTTPS 混合加密过程中非对称加密所使用的公钥。客户端有了这个可信的非对称加密公钥，就可以进行后续的混合加密会话密钥交换。

解决篡改问题：完整性校验

加密保护的是数据的机密性（防止窃听），但不一定保护数据的完整性（防止篡改）。攻击者即使不知道密文的具体内容，在某些加密模式下仍可能通过修改密文中的比特，对解密后的明文造成可预测的影响。因此，我们还需要一种机制来确保数据在传输过程中没有被修改，即数据完整性校验。

在 HTTPS/TLS 中，传统做法是通过消息认证码（MAC，Message Authentication Code）实现完整性保护。

消息认证码的计算依赖于一个共享密钥（通常由 TLS 握手协商出的会话密钥材料派生而来）和一个哈希函数。发送方根据数据和密钥计算出 MAC，并将其随数据一起发送。接收方收到数据后，使用相同的密钥重新计算 MAC，再与收到的 MAC 比较。如果一致，说明数据没有被篡改，并且来自持有对应密钥的一方；如果不一致，则说明数据无效。

MAC 的计算可以简单理解为：
```
MAC = HMAC-SHA256(密钥, 数据)
```

其中 HMAC（Hash-based Message Authentication Code）是一种基于哈希函数和密钥构造消息认证码的方法。

不过需要补充一个现代 TLS 很重要的变化：上面这种“加密 + 单独计算 MAC”的描述更适合帮助理解 TLS 1.2 及更早的一些密码套件。现代 TLS，尤其 TLS 1.3，主要使用 AEAD 算法，例如 AES-GCM、ChaCha20-Poly1305，把“加密”和“完整性认证”结合起来，不再单独使用 HMAC 给每条应用数据计算 MAC。

另外，MAC 本身不能单独解决重放攻击。例如攻击者虽然无法修改一个合法数据包，却可能把之前截获的合法数据重新发送。TLS 会通过记录序号等机制，让每条 TLS Record 处于特定的通信上下文中，从而使旧数据不能简单地被重新插入当前数据流。

所以可以把这部分知识压缩成一句话：加密解决“别人看不懂”，完整性认证解决“别人改不了”，序号等协议机制解决“别人不能把旧消息随便拿来再用”。

TSL协议的核心是握手协议，它负责在客户端和服务器之间协商加密参数、验证身份、生成会话密钥，为后续的安全通信奠定基础。
